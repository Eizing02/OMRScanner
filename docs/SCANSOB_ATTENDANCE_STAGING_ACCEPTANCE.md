# ผลตรวจรับ ScanSob สำหรับระบบเช็คชื่อ

งานรอบนี้เปลี่ยนชื่อที่ครูเห็นและแยกการพักรับคำขอใหม่ออกจากการจัดการคำขอเดิม ตรวจด้วยข้อมูลจำลองในเครื่อง เวอร์ชันคะแนน `1.0` และสัญญาระหว่างระบบใช้ต่อได้ตามเดิม

| รายการ | ผลในเครื่อง | ผลบน staging |
| --- | --- | --- |
| เวอร์ชันและค่าตั้ง | ชุดทดสอบ ScanSob ใช้ SQL 024 ใน PostgreSQL จำลอง ฝั่งระบบเช็คชื่อใช้ HTTP handler และ SQL `20261117_02_scansob_review_each_request.sql` จาก checkout `7e8113a` พร้อมงานที่ทีมฝั่งนั้นมีในเครื่อง | ยังไม่ได้ยืนยัน SQL 024, HTTPS origin, UUID โรงเรียน และคีย์ของ staging ทั้งสองฝั่ง ชื่อ deploy และ commit ที่ deploy ยังไม่มีหลักฐานยืนยัน |
| ชื่อระบบและโรงเรียน | หน้าตั้งค่า พรีวิวส่งคะแนนและสถานะส่ง/ถอนแสดง “ระบบเช็คชื่อ” ตรวจทั้ง fallback จาก connection เดิมและชื่อโรงเรียนจริง | รอเปิดหน้าจอจาก deploy ที่จะตรวจรับ |
| ขออนุมัติโดยไม่ลงอีเมล | ตัวรับในเครื่องรับบัญชีจำลองสองบัญชีนอกรายชื่อ แอดมินอนุมัติหนึ่งและปฏิเสธอีกหนึ่ง ตรวจสิทธิ์ inbox และห้ามเปิดคำขอใหม่ด้วยรหัส ฝั่ง ScanSob ทดสอบขอบเขต Workspace ที่ฐานข้อมูล | รอทดสอบ Google OAuth และ Workspace จริงของบัญชีทดสอบ A และ B |
| คำขอซ้ำ คำตอบหาย และพักรับ | การทดสอบสองฐานจำลองคำตอบหายหลังตัวรับบันทึกคำขอ พักรับทั้งสองฝั่ง แล้วตรวจว่า ScanSob ส่ง JSON เดิมก่อน `status` กล่องคำขอยังคงมีสองรายการ ตัวรับปิดเส้นทางรหัสและเพิกถอนได้ระหว่างพักรับ | รอจำลองการตอบกลับหายหลัง commit และกดจากสองแท็บบน deploy ที่จะตรวจรับ |
| อนุมัติและคิวส่ง | ทดสอบ SQL 024 ว่า `active` ใช้โหมด `manual` และคิวของ Workspace ที่เพิ่งอนุมัติเป็นศูนย์ | รอตรวจคิวฝั่ง ScanSob ก่อนกดส่งด้วยบัญชี A |
| ส่งและถอนคะแนน | ส่งคะแนนจาก ScanSob ไปยัง HTTP handler ของระบบเช็คชื่อในเครื่อง ทั้งสองฝั่งบันทึกรอบ 1 ตรงกัน รับหนึ่งรายการและจับคู่ไม่ได้หนึ่งรายการ ส่งซ้ำหลังคำตอบหายยอดไม่เพิ่ม การถอนรอบ 2 ยืนยันสำเร็จทั้งสองฝั่ง | รอเทียบใบตอบรับเลขรอบเดียวกันจากทั้งสองหน้าบน staging |
| การเชื่อมต่อเดิม | ตัวรับทดสอบส่งและถอนระหว่างพักรับด้วย token จากการเชื่อมต่อเดิม ScanSob แสดงชื่อใหม่โดยแปล fallback ตอนแสดงผล | รอตรวจ connection เดิมใน Workspace ทดสอบ |

ScanSob ผ่าน Vitest 85 รายการในชุดที่เกี่ยวข้อง เพิ่มอีกหนึ่งกรณีที่รันจริงข้ามสองฐานใน [`score-integration-review-receiver.test.ts`](../tests/score-integration-review-receiver.test.ts) โดยใช้ `MATHQUEST_SOURCE_DIR` ชี้ไปยัง checkout ฝั่งระบบเช็คชื่อ Playwright ผ่าน 8 กรณี รวมเดสก์ท็อป โทรศัพท์ และ iPad จำลอง สถานะและผลส่งล่าสุดอยู่ในกล่องส่งคะแนนของหน้าผลสอบ ประวัติ audit ที่จัดเก็บในฐานข้อมูลใช้ข้อมูลเดิม

Production build ในเครื่องผ่าน compile และ TypeScript ก่อนหยุดที่ขั้นรวบรวมข้อมูลของ `/api/scan-records` เพราะ Windows Application Control บล็อก `sharp` ต้องยืนยัน build สำเร็จจากสภาพแวดล้อม deploy ก่อนตรวจรับออนไลน์

## เมื่อตรวจรับบน staging

1. ระบุ SHA ของ ScanSob และระบบเช็คชื่อที่ deploy พร้อมชื่อหรือ ID ของ deploy ทั้งสองหน้า ยืนยันแถว SQL 024 ใน ScanSob และเวอร์ชัน Edge Function ของระบบเช็คชื่อ
2. ยืนยันว่าค่าปลายทางเป็นของ staging ทั้งสองฝั่ง ใช้ UUID ตรงกันและตั้ง `MATHQUEST_DESTINATION_LABEL` เป็นชื่อโรงเรียนจริง หากเดิมใช้คำว่า `MathQuest` เป็นชื่อระบบ ให้ใส่ `ระบบเช็คชื่อ` แทนในค่าตั้งนั้น ดู [ค่าตั้งและเงื่อนไขการพักรับ](MATHQUEST_SIGNED_PAIRING.md)
3. ตรวจแต่ละแถวของตารางด้วยบัญชีและข้อมูลจำลอง บันทึกสถานะผ่านหรือไม่ผ่านกับขั้นตอนแก้ อย่าใส่ token, signing key, session หรือข้อมูลนักเรียนจริงในรายงาน เก็บ flags ของ Production ตามค่าปัจจุบันระหว่างตรวจ staging
