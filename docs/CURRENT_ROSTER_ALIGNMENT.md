## เทียบฐานข้อมูล Supabase จริง

ตรวจผ่าน Supabase Dashboard ของโปรเจกต์ `bbtgulutbvxeafktntxg` ด้วยคำสั่ง SELECT เฉพาะ `information_schema.columns` ของ `public.students` ไม่อ่านข้อมูลบุคคล ไม่เรียก migration และไม่เขียนข้อมูลลงคลาวด์

```sql
select column_name, data_type, character_maximum_length, is_generated
from information_schema.columns
where table_schema = 'public' and table_name = 'students'
order by ordinal_position;
```

ได้ 13 คอลัมน์: `id`, `school_id`, `student_code`, `first_name`, `last_name`, `classroom_name`, `number`, `created_at`, `updated_at`, `prefix`, `full_name`, `grade_level`, `room`

| คอลัมน์ในไฟล์/หน้าจอ | ช่องเก็บจริง | วิธีเก็บ |
| --- | --- | --- |
| รหัสประจำตัว | `student_code` | varchar(5) เป็นข้อความ เก็บศูนย์นำหน้า |
| ชื่อ | `prefix` + `first_name` | text แยกคำนำหน้าเพื่อใช้งานภายใน แต่แสดงรวมในช่องชื่อ |
| นามสกุล | `last_name` | text |
| ระดับชั้น | `classroom_name` | text เช่น ม.1/1 หรือ ม.6 ไม่มีการแต่งห้องที่ไม่มีในไฟล์ |

`full_name` (text), `grade_level` (text) และ `room` (integer) เป็น generated ALWAYS; ชั้นไม่มีห้องมี room เป็น null. `number` เว้นว่างได้ ระบบไม่ตั้งเลขที่ขึ้นเอง. `id`/`school_id` เป็น UUID และ timestamps เป็น timestamp with time zone.

ไม่ต้องเพิ่ม SQL หรือเปลี่ยนชื่อช่องฐานข้อมูลสำหรับรูปแบบนี้ การยืนยันนี้ครอบคลุมคอลัมน์นักเรียน ไม่ใช่การรับรองทุก migration/RLS/Google Login/ระบบ OMR สด

## การแก้ไขที่ทำ

- เพิ่ม alias `ระดับชั้น` ในตัวจับคู่คอลัมน์อัตโนมัติ
- หน้านำเข้าใช้สี่ mappings ตามลำดับไฟล์ พร้อมตัวอย่าง CSV ใหม่และพรีวิวชื่อ/นามสกุลแยกกัน
- ตารางนักเรียนใช้สี่คอลัมน์เดียวกับต้นฉบับ คงค้นหา ตัวกรอง และแบ่งหน้า
- ไฟล์ชื่อ-สกุลรวมแบบเดิมยังนำเข้าได้ ส่วนเลือก mapping จะเปิดอัตโนมัติเมื่อพบคอลัมน์ชื่อ-สกุลรวม
- ป้องกันรหัสซ้ำทั้งในไฟล์และกับทะเบียนเดิมเหมือนเดิม ไม่เขียนทับหรือย้ายชั้นโดยอัตโนมัติ
- คงระบบภาพ สี ฟอนต์ และส่วนประกอบเดิม; ไม่เปลี่ยน DESIGN.md หรือ design.json ในส่วนเสริมนี้

## ผลทดสอบและขอบเขต

- ข้อมูลจริงทั้งสองไฟล์: 202 แถวผ่าน schema และเทียบกลับต้นฉบับ (อ่านเฉพาะในเครื่อง ไม่เป็น fixture ที่ commit)
- Unit: `npx vitest run --maxWorkers=2` ผ่าน 83/83 ใน 14 ไฟล์; รอบรันพร้อม dev server/lint ด้วย concurrency ปกติมี timeout 5 วินาทีในสองชุดทดสอบโลโก้ จึงรันซ้ำแบบจำกัด worker โดยไม่แก้โค้ด/timeout ของการทดสอบ
- E2E เฉพาะ current-roster และ roster-logo: ผ่าน 7/7 รวมไฟล์สี่คอลัมน์ CSV/XLSX, สามคอลัมน์เดิม, formatted ID, validation/pagination, และการถดถอยโลโก้/PDF
- Typecheck, ESLint และ production build (Next.js 16.4.0) ผ่าน
- Desktop 1440 และ mobile 390: Axe WCAG2A/AA/2.1AA ไม่พบข้อผิดพลาดที่ตรวจอัตโนมัติ หน้าไม่มี horizontal overflow; ตารางเลื่อนภายในได้
- Impeccable detect บนสองหน้าจอ TSX: ไม่พบ findings. ภาพหลักฐานเป็นรายชื่อสังเคราะห์เท่านั้นใน `.impeccable/review/roster-four-{import,list}-{desktop,mobile}.png`

ตอนตรวจรายชื่อยังไม่ได้ commit/push/deploy และยังไม่อัปโหลดรายชื่อจริงขึ้น Supabase. การเผยแพร่โค้ดรอบถัดไปบันทึกใน [GITHUB_RELEASE_20261009.md](GITHUB_RELEASE_20261009.md). การตรวจคอลัมน์ไม่ทดแทนการทดสอบนำเข้าจริงผ่านบัญชีที่ยืนยัน Google และได้รับสิทธิ์แล้ว

ไฟล์นี้เป็นทะเบียนปัจจุบัน ระบบยังไม่มีประวัติสมาชิกห้องแยกตามเทอม/ปี. หากมีรหัสเดียวกันจากทะเบียนเก่า ระบบจะบล็อกและให้ตรวจสอบ ไม่ merge หรือเขียนทับข้อมูลเดิม. ต้องออกแบบการเลื่อนชั้น/เก็บประวัติแยกก่อนเปลี่ยนพฤติกรรมนั้น

ก่อนนำเข้าข้อมูลจริง ต้องตั้ง Google OAuth/redirects และจัดการคีย์ legacy service_role ที่เคยเปิดเผยในแชตให้เสร็จ; ห้ามใส่ service_role ในหน้าเว็บหรือใช้มันแทนสิทธิ์ครู

## ตรวจหน้าจอและเอกสาร

ผล finish reviewer อิสระ: `disposition: ship` สำหรับส่วนเสริมนำเข้า/แสดงรายชื่อสี่คอลัมน์นี้เท่านั้น Persistence, fidelity, finish ceiling และสิ่งที่ต้องคงไว้สอดคล้องกับระบบเดิม; `material fixes: none` ภาพ desktop/mobile ทั้งสี่ใช้ได้ มือถือจัด mappings สองคอลัมน์และเลื่อนตารางภายในเป็นการปรับตามอุปกรณ์ในระบบเดิม

Documenter เปิดภาพสังเคราะห์ทั้งสี่และเทียบ surface brief, `DESIGN.md` และ CSS เฉพาะส่วนแล้ว บันทึกภาพและคำตัดสินไว้ใน [CURRENT_ROSTER_DESIGN_EVIDENCE.md](CURRENT_ROSTER_DESIGN_EVIDENCE.md). คง `DESIGN.md` และ `.impeccable/design.json` ไม่สร้างโลกภาพ, comp, token หรือ raster ใหม่ และไม่มีการเปลี่ยน provenance ของภาพที่ใช้งานอยู่

มีความคลาดเคลื่อนเดิมใน narrative ของ sidecar สำหรับ Designer มือถือและข้อความ Stack ที่ยังเป็นแผนเก่าใน `PRODUCT.md`; รายงานตามหลักฐานโดยไม่ซ่อมหรือยกเป็นกฎใหม่ในงานรายชื่อนี้ คำตัดสิน ship ไม่รับรองระบบ OMR ทั้งผลิตภัณฑ์ การตั้ง Auth หรือการนำเข้าข้อมูลจริงบนคลาวด์
