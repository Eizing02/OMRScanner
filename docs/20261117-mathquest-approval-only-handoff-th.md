# งานส่งต่อ MathQuest สำหรับอนุมัติสิทธิ์ส่งคะแนนจาก ScanSob

วันที่ 17 พฤศจิกายน 2569 · ข้อกำหนดสำหรับทีมระบบเช็คชื่อและ ScanSob

เอกสารนี้ใช้แทนขั้นตอนกรอกรหัสและลงรายชื่อครูล่วงหน้าในแผนรอบก่อน สำหรับการเปิดรับคำขอใหม่ตามขั้นตอนด้านล่าง อ้างอิงโค้ด ScanSob `a304e93` และ MathQuest `7e8113a` ที่ตรวจในเครื่อง สถานะของ Netlify และ Supabase ที่ใช้งานจริงต้องตรวจแยกก่อนเปิดใช้

## ผลที่ต้องการ

1. ครูเข้า ScanSob ด้วย Google ใช้บัญชีที่ได้รับอนุมัติให้ทำงานในพื้นที่ของตน เปิด **การตั้งค่า → เชื่อมต่อระบบเช็คชื่อ** แล้วกด **ขออนุมัติส่งคะแนน** สำหรับโรงเรียนปลายทางที่ระบบแสดง
2. คำขอเข้ากล่องของแอดมิน MathQuest พร้อมชื่อและอีเมล Google ที่ยืนยันแล้ว ชื่อพื้นที่ทำงาน โรงเรียนปลายทาง และเวลาที่ขอ แอดมินตรวจว่าครูบัญชีนี้มีหน้าที่ส่งคะแนนให้โรงเรียน แล้วกด **อนุมัติ** หรือ **ปฏิเสธ** รายคำขอ
3. เมื่อแอดมินอนุมัติและ ScanSob รับสิทธิ์สำเร็จ ครูจึงกด **ส่งคะแนนไประบบเช็คชื่อ** จากชุดสอบที่มีคะแนนยืนยันแล้ว การอนุมัติเริ่มในโหมดกดส่งเองและต้องมีงานส่งในคิวเป็นศูนย์ การส่งคะแนน การถอนคะแนน และใบตอบรับใช้ระบบเดิม

| เรื่อง | ใครตัดสินใจ | ขอบเขต |
| --- | --- | --- |
| อนุมัติบัญชี ScanSob | ผู้ดูแล ScanSob | สิทธิ์ใช้งานพื้นที่ของครู |
| อนุมัติคำขอส่งคะแนน | แอดมิน MathQuest ที่มีสิทธิ์จัดการการเชื่อมต่อของโรงเรียน | `score:write` สำหรับพื้นที่ต้นทางและโรงเรียนปลายทางตามคำขอ |
| เผยแพร่คะแนน | ครูในพื้นที่ที่ได้รับสิทธิ์ | ชุดสอบและรอบที่ครูกดส่งหลังยืนยันคะแนน |

ครูไม่ต้องกรอกรหัสเชื่อมต่อ ส่งโค้ดผ่านแชต หรือขอให้แอดมินลงอีเมลก่อน สิทธิ์ที่ได้รับครอบคลุมการส่งคะแนนตามสัญญาเดิม บัญชี ScanSob ไม่มีสิทธิ์ดูข้อมูลเช็คชื่อหรือเข้าหน้าแอดมินจากการอนุมัตินี้ ผู้ดูแลระบบตั้งค่าลายเซ็นระหว่างเซิร์ฟเวอร์ครั้งเดียวต่อสภาพแวดล้อม

## งานของฝั่ง MathQuest

### 1. เพิ่มโหมดรับคำขอให้แอดมินพิจารณารายบัญชี

ทำ migration เพิ่มในโปรเจกต์ MathQuest โดยอิง schema จาก `20261015_03_scansob_recovery_hardening.sql` และ `20261116_01_scansob_code_free_pairing.sql` ตรวจสถานะการติดตั้งจริงของฐานก่อนตั้งชื่อและเรียง migration `20261117_01_scansob_publication_receipts.sql` เป็นงานรายงาน ให้คงการทำงานเดิม

- เพิ่มนโยบายรับคำขอรายโรงเรียน เช่น `review_each_request` โดยค่าเริ่มต้นของ migration รักษานโยบายเดิมไว้จนกว่าจะสลับโหมด เก็บรายชื่อเก่าไว้สำหรับย้อนกลับระหว่างปล่อยรุ่น โหมดปลายทางสำหรับผู้ใช้จริงคือพิจารณาทีละคำขอโดยใช้รายการรออนุมัติเท่านั้น
- `mq_scansob_prepare_signed` ให้ตรวจโรงเรียนที่ตั้งไว้กับรอบเปิดรับ และตรวจโครงสร้างคำขอ โดยเอาการ `join` ตารางอีเมลออกเมื่อใช้นโยบายใหม่ ครูที่ผ่านเงื่อนไขต้นทางจึงเตรียมคำขอได้แม้ไม่เคยมีชื่อใน MathQuest
- `mq_scansob_request_signed` ให้ข้ามเงื่อนไขรายชื่ออีเมลเฉพาะสาขาที่สร้างคำขอใหม่ในนโยบายใหม่ รักษาการตรวจลายเซ็น รอบเปิดรับ อัตราการเรียก การล็อก และเงื่อนไขหนึ่งคำขอรอหรือหนึ่งการเชื่อมต่อที่ยังใช้งานต่อคู่โรงเรียน–พื้นที่ ให้ตรวจคำขอเดิมก่อนตรวจประตูรับงานใหม่ เพื่อให้ส่งซ้ำคำขอเดิมได้หลังเปลี่ยนนโยบายตามเงื่อนไขเดิม
- `mathquest_private.scansob_check_signed_approval` ให้ยกเลิกเงื่อนไขอีเมลที่ลงรายชื่อไว้ในนโยบายใหม่ รักษาการตรวจหมดอายุด้วยเวลาจริง สถานะ `pending_approval` ความขัดแย้งกับคำขออื่น และการอนุมัติแบบอะตอมิก ตรวจว่า `approve`/`reject` ของ `mq_scansob_admin` ใช้ผู้ดูแลที่ยืนยันตัวตนและอยู่เขตโรงเรียนปลายทางจริง ปัจจุบันใช้ `mathquest_private.require_teacher` ซึ่งตรวจบัญชี Google ครูที่ตั้งไว้และ session ที่ผูกบัญชีนั้น หากมีบทบาทครูเพิ่มภายหลัง ให้ยืนยันสิทธิ์ผู้ดูแลการเชื่อมต่อแยกจากสิทธิ์ครูทั่วไปใน RPC
- `mq_scansob_pairing_inbox` ให้ `configure` เปิดโหมดใหม่ได้โดยไม่มีรายชื่ออีเมล รักษาการตรวจ revision ของนโยบายและบันทึกผู้เปลี่ยนค่า กำหนดให้การปิดรับหยุดคำขอใหม่ แต่แอดมินยังตัดสินคำขอที่รับสำเร็จแล้วได้จนหมดอายุ และคำขอเดิมยังตรวจสถานะหรือยกเลิกได้ การปิดแล้วเปิดหรือเปลี่ยนนโยบายต้องสร้าง `pairing_window_id` ใหม่ เพื่อให้คำขอที่เพียงเตรียมไว้ในรอบเก่าใช้เปิดรายการใหม่ไม่ได้
- จำกัด RPC รับคำขอลงนามไว้ที่ Edge Function ตามสิทธิ์เดิม นักเรียน ผู้ใช้ที่ยังไม่เข้าสู่ระบบ และครูที่ไม่มีสิทธิ์แอดมินต้องเรียกอ่านกล่องคำขอ ตั้งค่า หรืออนุมัติโดยตรงไม่ได้ บันทึกผู้ขอ ผู้ตัดสินใจ การเปลี่ยนนโยบาย และเวลาของแต่ละเหตุการณ์ตามโครงสร้าง audit เดิม เก็บอีเมลในข้อมูลคำขอที่จำกัดสิทธิ์เข้าถึง

### 2. ใช้หน้ากล่องคำขอที่มีอยู่

- ปรับ `index.html` และ `scansob-inbox.js` ให้กล่อง **คำขอจาก ScanSob** แสดงชื่อ อีเมล พื้นที่ทำงาน โรงเรียนปลายทาง เวลาขอ และเวลาหมดอายุ พร้อมปุ่ม **อนุมัติ** และ **ปฏิเสธ** รายรายการ หากกดพร้อมกันสองแท็บ ให้การตัดสินครั้งแรกมีผลเพียงครั้งเดียวและแท็บที่สองโหลดสถานะล่าสุด
- เอาช่องลงรายชื่ออีเมลและเมนูสร้างรหัสออกจากขั้นตอนใช้งานปกติ เมื่อเปิดนโยบายใหม่ UI แอดมินมีการเปิดหรือพักรับคำขอ และเข้าจัดการรายการเดิมได้ รักษากระดิ่งแจ้งเตือนและสิทธิ์กล่องคำขอเดิม
- ตอนสลับใช้งานจริง ปิดการสร้างรหัสใหม่ที่ `mq_scansob_admin('create_code')` และการเปิดคำขอใหม่ด้วยรหัสที่ `mq_scansob_pair('request')` ฝั่งเซิร์ฟเวอร์ด้วย รหัสที่ยังไม่ถูกใช้ต้องเปิดคำขอใหม่ไม่ได้ คำขอแบบเดิมที่เข้าคิวแล้วจัดการต่อได้จนหมดอายุ การเชื่อมต่อที่อนุมัติแล้ว สิทธิ์ที่เก็บไว้ ใบตอบรับ และประวัติคะแนนยังใช้ได้
- แอดมินควรตรวจว่าบัญชีผู้ขอมีสิทธิ์ส่งคะแนนให้โรงเรียนนี้ก่อนกดอนุมัติ ตัวรับคะแนนจับคู่จากรหัสนักเรียนห้าหลักในทะเบียนของ MathQuest ปลายทาง รหัสชุดเดียวกันอาจมีอยู่ต่างโรงเรียน จึงใช้ชื่อพื้นที่และอีเมลเพื่อช่วยตรวจครูโดยไม่เปิดข้อมูลนักเรียนในคำขอ

### 3. รักษาสัญญาระหว่างระบบ

- ใช้ `POST /functions/v1/pair-scansob-workspace` ต่อ โดยให้ `prepare_signed` และ `request_signed` ผ่าน HMAC-SHA-256 บนไบต์คำขอจริง รับ `sender_auth_id` และ `sender_verified_email` ที่ ScanSob ตรวจและลงนามให้ ผูก request กับ UUID ของพื้นที่และโรงเรียนปลายทางตามเดิม รักษาการจำกัดจำนวนคำขอและ `Retry-After`
- คำตอบ `prepare_signed` รุ่น `1.0` ใช้ฟิลด์ `schema_version`, `action`, `request_id`, `destination_school_id`, `pairing_window_id` เท่าเดิม เพราะ ScanSob ตรวจแบบ strict ถ้าต้องเพิ่มตัวบอกความสามารถของ receiver ให้ใช้สัญญาที่ตกลงแยกต่างหาก สำหรับรอบนี้ให้ทดสอบจริงด้วยบัญชีที่ไม่อยู่ในรายชื่อก่อนตั้ง flags ว่าผ่านการตรวจแล้ว
- คำตอบหลัง `request_signed` ใช้ `pending_approval`, `active`, `rejected` หรือ `expired` ตามสัญญาเดิม รักษา `status` และ `revoke` ที่ใช้ challenge ของคำขอ และช่องทางส่ง token ของการเชื่อมต่อเดิม เมื่อการตอบกลับ `request_signed` หายหลังบันทึก ให้รับการส่งซ้ำด้วย ID และเนื้อหาเดิมแล้วคืนสถานะเดียวกับคำขอเดิม
- `ingest-scansob-results` ใช้สัญญาคะแนน `1.0` และ `score:write` ตามเดิม รักษาการป้องกันบันทึกซ้ำ ใบตอบรับแยกชุดสอบและรอบ พฤติกรรมถอนคะแนน และการรายงาน `STUDENT_NOT_FOUND` สำหรับรหัสที่ไม่อยู่ในทะเบียนปลายทาง

## งานของฝั่ง ScanSob

1. ใน `components/integrations/mathquest-settings.tsx` เปลี่ยนการ์ดเป็นปุ่ม **ขออนุมัติส่งคะแนน** พร้อมชื่อโรงเรียนและข้อความสั้น เช่น “เมื่ออนุมัติแล้ว คุณจะส่งรหัสนักเรียนและคะแนนที่ยืนยันไปยัง MathQuest ของโรงเรียนนี้ได้” ให้การกดปุ่มหลังเห็นข้อความเป็นการยืนยันส่งคำขอครั้งนั้น และคง `consent: true` ที่ผ่านการตรวจบนเซิร์ฟเวอร์ตามสัญญาปัจจุบัน
2. เอาช่องกรอกรหัส ตัวสลับใช้รหัส และการย้อนกลับไปแสดงฟอร์มเดิมเมื่อเช็กปลายทางไม่ผ่านออกจาก UI ครู แยกข้อความ **ปลายทางยังไม่เปิดรับคำขอ** เมื่อได้รับผลว่าปิดรับ กับ **ตรวจสถานะปลายทางไม่ได้ ลองใหม่** เมื่อเชื่อมต่อไม่ได้หรือยังตรวจความพร้อมไม่สำเร็จ ให้ API คืนสถานะที่ UI ใช้ได้โดยไม่เผยค่าลับ เมื่อเปิดใช้งานร่วมกันให้ปิดการส่งคำขอใหม่แบบกรอกรหัสที่ API ด้วย
3. รักษาขอบเขตบัญชีและพื้นที่ใน `app/api/integrations/mathquest/route.ts` ใช้ผู้ใช้ที่เข้าสู่ระบบและได้รับอนุมัติ ตรวจอีเมล Google จาก session ที่เซิร์ฟเวอร์อ่านเอง การเข้าไปดูพื้นที่ครูอื่นแบบอ่านอย่างเดียวต้องส่งคำขอแทนไม่ได้
4. แสดง **รออนุมัติ** หลัง MathQuest ตอบรับแล้ว และ **เชื่อมต่อแล้ว** เมื่อยืนยันปลายทางและบันทึกสิทธิ์สำเร็จ ให้ตรวจสถานะและยกเลิกได้ตามเดิม ถ้าผลส่งไม่แน่ชัดให้กู้คำขอเดิมก่อนเปิดรายการใหม่ หากคำตอบ `prepare_signed` ของการขอจริงหาย ให้ยกเลิก attempt เดิมตามสัญญาก่อนเริ่มใหม่ หากคำตอบ `request_signed` หาย ให้ส่งซ้ำด้วย ID และ JSON เดิมก่อนเรียก `status` รองรับทั้งกรณีปฏิเสธและหมดอายุ
5. ใช้การจัดเก็บและขั้นตอน retry จาก [SQL 024](../supabase/migrations/202611170024_mathquest_signed_pairing.sql) เป็นฐาน งาน UI และตัวปิดการเปิดคำขอแบบเก่าไม่ควรต้องมี SQL ใหม่ใน ScanSob หากตรวจแล้ว schema และ RPC ที่ติดตั้งรองรับครบ ส่งงานแก้ไข SQL ของ MathQuest ให้ทีม MathQuest ติดตั้งในฐานของตนเท่านั้น

## ลำดับปล่อยและตรวจรับ

| ฝั่ง | ค่าที่ผู้ดูแลระบบต้องตั้งใน staging ก่อน |
| --- | --- |
| ScanSob server | `MATHQUEST_RECEIVER_ORIGIN`, `MATHQUEST_DESTINATION_SCHOOL_ID`, `MATHQUEST_DESTINATION_LABEL`, `MATHQUEST_CODE_FREE_SIGNING_KEY_ID`, `MATHQUEST_CODE_FREE_SIGNING_KEY` และ flags การส่งคะแนนเดิม `SCORE_INTEGRATION_ENABLED`, `MATHQUEST_RECEIVER_VERIFIED` |
| ScanSob flags รับคำขอ | `MATHQUEST_CODE_FREE_PAIRING_ENABLED` และ `MATHQUEST_CODE_FREE_PAIRING_RECEIVER_VERIFIED` เริ่มที่ `false` ให้ทีมเปิดใน staging หลังตรวจปลายทางเบื้องต้น และเปิดใน production หลังตรวจรับครบ |
| MathQuest Edge Function | `SCANSOB_CODE_FREE_SIGNING_KEY_ID`, `SCANSOB_CODE_FREE_SIGNING_KEY`, `SCANSOB_CODE_FREE_DESTINATION_ID` ตรงกับค่าฝั่ง ScanSob ของสภาพแวดล้อมเดียวกัน และคง `SCANSOB_PAIRING_DELIVERY_KEY` สำหรับส่งมอบสิทธิ์ตามระบบเดิม |

1. **MathQuest staging** ตรวจ receiver และ migration ที่ใช้อยู่ ก่อนติดตั้ง migration เพิ่ม ปล่อยหน้าแอดมินและ Edge Function ที่ตรงกับสัญญาเดิม เปิดโหมดใหม่สำหรับปลายทางทดสอบ ทีมระบบตั้ง destination UUID และคีย์ลงนามจากฝั่งเซิร์ฟเวอร์ให้ตรงกัน
2. **ScanSob staging** ตรวจ SQL 024 และค่าตั้งทั่วไปของตัวส่งคะแนน จากนั้นเปิด flags การจับคู่แบบไม่ใช้รหัสใน staging ตาม [คู่มือการลงนาม](MATHQUEST_SIGNED_PAIRING.md) ทดสอบด้วยบัญชี Google จำลองที่ ScanSob อนุมัติแล้วและไม่มีแถวใน `scansob_pairing_teachers` ใช้ข้อมูลนักเรียนจำลอง ตรวจผล release check ของ commit ที่จะ deploy ให้ผ่าน
3. **ทดสอบสองฝั่ง** ทดสอบตามตารางด้านล่าง เก็บ commit ของเว็บทั้งสองฝั่ง ชื่อ migration เวอร์ชัน Edge Function และผลทดสอบโดยใช้ข้อมูลจำลอง
4. **เปิดใช้จริงหลังได้รับอนุมัติ** ปล่อย receiver ที่รองรับนโยบายใหม่ก่อนโดยรักษาพฤติกรรมเดิมไว้ จากนั้นตรวจ release ของ ScanSob และนัดสลับพร้อมกัน เปิดรับคำขอแบบรายบัญชี เปิด flags ฝั่ง ScanSob และปิดทางเปิดคำขอใหม่ด้วยรหัสทั้งสองฝั่ง ตรวจหน้าเว็บจริงว่าขึ้นปุ่มใหม่และคำขอตัวอย่างถึงกล่องแอดมิน
5. **ถ้าพบปัญหา** พักการรับคำขอใหม่ฝั่ง MathQuest และปิด flag รับคำขอใหม่ฝั่ง ScanSob ตามขอบเขตที่มีปัญหา เก็บ origin, destination, คีย์ส่งมอบ และช่องทาง `status`/`revoke` ให้คำขอเดิมทำงานได้ การพักรับคำขอไม่ควรระงับสิทธิ์เดิมหรือเปลี่ยนคะแนนที่ส่งแล้ว

| กรณีตรวจรับ | ผลที่ต้องได้ |
| --- | --- |
| ครูที่ได้รับอนุมัติใน ScanSob แต่ไม่อยู่ในรายชื่ออีเมล MathQuest กดขอครั้งเดียว | ไม่มีช่องรหัสและเกิดคำขอรออนุมัติหนึ่งรายการ เลขคำขอตรงกันสองฝั่ง ขณะรอยังส่งคะแนนไม่ได้ |
| แอดมิน MathQuest อนุมัติบัญชี A และปฏิเสธบัญชี B | A เชื่อมสำเร็จในโหมดกดส่งเองและไม่มีงานคะแนนถูกสร้างขึ้น B เห็นสถานะปฏิเสธและไม่มีสิทธิ์ส่ง A และ B ตรวจสถานะของกันและกันไม่ได้ |
| ผู้ใช้ที่ไม่มีสิทธิ์กดยิงคำขออนุมัติโดยตรง | การเรียกอ่านกล่องคำขอ อนุมัติ ปฏิเสธ และตั้งค่าถูกปฏิเสธที่ API/RPC |
| คำตอบหาย กดซ้ำ เปิดสองแท็บ หรืออยู่คนละรอบเปิดรับ | ใช้คำขอเดิมโดยไม่เพิ่มรายการซ้ำ การอนุมัติมีผลครั้งเดียว คำขอหมดอายุและ attempt ที่ใช้รอบเก่าเปิดรายการใหม่ไม่ได้ |
| เปิดโหมดใหม่แล้วพบการเชื่อมต่อเดิมและคำขอเดิม | รายการที่เชื่อมแล้วส่งคะแนนได้ตามสิทธิ์เดิม คำขอเดิมจัดการได้ รหัสที่ยังไม่ใช้เปิดคำขอใหม่ไม่ได้ |
| พักรับคำขอหรือปลายทางขัดข้อง | ScanSob แสดงสถานะตรงสาเหตุ ผู้ใช้ยังตรวจสถานะหรือยกเลิกคำขอเดิมได้เมื่อปลายทางพร้อม |
| ส่งคะแนนจำลองหลังยืนยันและกดส่งเอง | รหัสทดสอบเช่น `02000` ยังมีศูนย์นำหน้า MathQuest รับคะแนนตามรอบและแสดงผลถูกบัญชี รหัสที่ไม่พบมีรายงาน กดส่งซ้ำไม่สร้างคะแนนซ้ำและทดสอบถอนได้ |

## สิ่งที่ขอให้ทีม MathQuest ส่งกลับ

- ลิงก์ PR หรือ commit ชื่อ migration และขั้นตอนเปิดหรือพักรับคำขอใหม่ เวอร์ชันของ `pair-scansob-workspace` ที่ทดสอบ
- หลักฐานจาก staging ว่าครูที่ไม่อยู่ในรายชื่อส่งคำขอถึงกล่องได้ แอดมินอนุมัติหรือปฏิเสธได้ การทดสอบสิทธิ์ผ่าน และการเชื่อมต่อเดิมยังส่งคะแนนได้
- ยืนยันว่าคำตอบ `prepare_signed` และสัญญาคะแนนรุ่น `1.0` ใช้กับ ScanSob ปัจจุบันได้ ถ้ามีข้อเสนอเปลี่ยนสัญญาให้ระบุฟิลด์และผลกระทบก่อนเปลี่ยน
- ระบุค่า public identity ของปลายทางทดสอบที่ใช้ร่วมกัน เช่น HTTPS origin และ UUID โรงเรียน ส่งคีย์ลงนามผ่านตัวจัดการ secrets ของแต่ละระบบ หลีกเลี่ยงการแนบคีย์และข้อมูลนักเรียนจริงในเอกสารหรือผลทดสอบ
